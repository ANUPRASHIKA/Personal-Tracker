Personal Tracker — Developer Guide

A walkthrough of every feature and the code flow behind it, written for a developer new to this codebase.

Overview & Tech Stack

Personal Tracker is a single-page React app for tracking work shifts, commute/expenses, and leave/WFH days, with a dashboard and reports. Data is stored per-user in Firestore so it syncs across devices after signing in with Google.

LayerChoice
UI frameworkReact 19 (function components + hooks only, no class components)
Build toolVite
Auth + DatabaseFirebase Authentication (Google sign-in) + Cloud Firestore
StylingPlain CSS with custom properties (src/index.css) — no CSS framework
Iconslucide-react
FontInter (self-hosted via @fontsource-variable/inter)
Excel import/export@e965/xlsx
HostingGitHub Pages, deployed via GitHub Actions on push to main

There is no backend server — the "backend" is Firestore directly, accessed from the browser using the Firebase client SDK and secured with Firestore security rules.

App Architecture

App.jsx nests providers from the outside in. Order matters: AuthProvider must wrap the code that decides whether to show the sign-in screen, and DataProvider (which needs the signed-in user's uid) is only mounted once a user exists.

Inside AppShell:

→
no user? → SignInScreen
→

Which page renders is controlled by a single activeTab string in AppShell's local state, looked up in a PAGES map:

const PAGES = { dashboard: Dashboard, shift: ShiftLog, commute: CommuteLog, leave: LeaveLog, reports: Reports, settings: Settings };
const Page = PAGES[activeTab];
...
<Page />

There's no router (no URL changes per tab) — it's a simple state-driven single view swap, which is enough for this app's size.

Component Interaction Map

Two different mechanisms carry data between components in this app — knowing which one applies where is the fastest way to trace a bug:

  • Props (explicit, parent → child): used for a handful of top-level wiring points, listed below.
  • Context hooks (implicit, any depth): useData(), useAuth(), useToast(), useTheme() — any component can call these directly without its parent passing anything down. This is how every page gets at shifts/commutes/etc. without App.jsx knowing or caring what each page needs.

Component tree

App ThemeProvider (context: theme, toggleTheme) AuthProvider (context: user, loading, signIn, signOutUser) AppShell — reads useAuth() directly SignInScreen — reads useAuth() directly (signIn) DataProvider (context: shifts/commutes/.../CRUD — wraps useUserData) ToastProvider (context: showToast) Header ← props: activeTab, onChangeTab, user, onSignOut Calculator — fully self-contained, no props, no context Page (Dashboard/ShiftLog/CommuteLog/LeaveLog/Reports/Settings) QuickPunch — reads useData() + useToast() directly (Dashboard only) BarChart / LineChart / ComboChart / DonutChart ← props: bars / segments SortableTh ← props: label, sortKey, activeKey, dir, onSort StatIcon / Badge / CategoryDot ← props only

Why Header gets user/onSignOut as props instead of calling useAuth() itself

AppShell already has to call useAuth() to decide whether to render the sign-in screen at all, so it passes the same user/signOutUser straight down to Header rather than having Header read the context a second time. activeTab/onChangeTab are plain useState in AppShell (not context) since only Header and the PAGES switch need them.

Rule of thumb when adding a component: if it needs tracker data, reach for useData() directly rather than threading props through several layers — that's the established pattern everywhere except the three props Header receives from AppShell.

Authentication AuthContext.jsx lib/firebase.js

lib/firebase.js initializes the Firebase app once and exports auth, googleProvider, and db (Firestore). The config object is a public client identifier, not a secret — it's fine to commit.

AuthContext.jsx listens to Firebase's auth state:

const [user, setUser] = useState(undefined); // undefined = not resolved yet
useEffect(() => onAuthStateChanged(auth, setUser), []);

value = {
  user: user ?? null,
  loading: user === undefined,
  signIn: () => signInWithPopup(auth, googleProvider),
  signOutUser: () => signOut(auth),
};

App.jsx reads loading/user from useAuth() to decide what to render (spinner → sign-in screen → app). Once signed in, user.uid becomes the Firestore document key for all of that person's data.

Displaying the logged-in user's details anywhere

user is the raw Firebase Auth user object (from Google sign-in), so any component can read its fields directly after calling useAuth() — no extra plumbing needed:

import { useAuth } from '../context/AuthContext';

function SomeComponent() {
  const { user } = useAuth();
  return (
    <>
      {user.photoURL && <img src={user.photoURL} alt="" />}
      <span>{user.displayName || user.email}</span>
    </>
  );
}

Useful fields on user: displayName, email, photoURL, uid, emailVerified, metadata.creationTime / metadata.lastSignInTime.

Header.jsx is the one exception to "just call useAuth()" — it receives user/onSignOut as props from AppShell instead, since AppShell already needs the auth state for the sign-in gate (see the Component Interaction Map section for why).

Multi-User Extension (viewing someone else's data)

Today the app is strictly single-tenant: each signed-in user can only ever read/write their own Firestore document (users/{uid}), enforced by the security rule in the Firebase Setup section. There is no built-in way to look up or display another user's data by email, and that's intentional — enabling it requires a deliberate access-control design, not a quick tweak.

Why you can't just "look up by email" today

  • Firestore documents are keyed by uid, not email — there's no query path from an email string to a document.
  • The Firebase client SDK has no API to resolve an email to a uid (that's an admin-only operation, admin.auth().getUserByEmail(), to prevent user-enumeration attacks).
  • Even with a uid in hand, the current security rule (request.auth.uid == userId) would reject the read.

How to extend it properly (a "sharing" feature)

  1. Email → uid index: a separate top-level collection, e.g. emailIndex/{email}: { uid }, written once at sign-up. Security rule allows any authenticated user to read this collection (but only write their own entry), so the client can resolve an email the owner wants to share with.
  2. Consent field on the owner's document: add sharedWith: [uid1, uid2, ...] inside users/{uid}, managed via a new updateSharedWith() method in DataContext (same pattern as updateLeaveSettings).
  3. Updated security rule: 
    allow read: if request.auth.uid == userId
  || request.auth.uid in resource.data.sharedWith;
  4. Parameterize the data hook: useUserData(uid) already takes a uid argument — the only change needed is letting DataProvider accept an optional "viewing uid" (defaulting to the signed-in user's own) so a page can say "load this other person's document instead".
  5. UI: an "Invite by email" control in Settings (writes to sharedWith after resolving via emailIndex), plus some way to switch between "my data" and "shared-with-me" views (e.g. a dropdown in the sidebar).

Keep any shared view read-only unless you also design write-conflict handling — two people editing the same shift/leave data concurrently is its own problem this app doesn't currently solve.

Data Layer & Firestore useUserData.js DataContext.jsx

Storage model

All of a user's data lives in one Firestore document: users/{uid}. There are no subcollections. The document looks like:

{
  shifts: [ { id, date, punchIn, punchOut, breakMin, callMin, notes } ],
  commutes: [ { id, date, type, period, route, routeRemark, mode, modeRemark, payment, paymentRemark, fare, notes } ],
  holidays: [ { id, date, name } ],
  leaves: [ { id, date, type, days, notes } ],
  wfhLogs: [ { id, date, notes } ],
  leaveSettings: { tenureEligible, annualOpeningBalance, annualOpeningDate }
}

This is deliberately simple (schemaless Firestore + whole-document read/write) because data volumes are small (one person's personal tracker) — there was no need for subcollections or paginated queries.

Load/save cycle — useUserData(uid)

uid changes
→
getDoc(users/uid)
→
setData(merged with defaults)
→
loadedUid.current = uid

A second useEffect watches data and calls setDoc(..., { merge: true }) on every change — but only after the initial load for that uid has completed (guarded by loadedUid.current === uid). This prevents the just-loaded data from being immediately (and redundantly/incorrectly) written back before the real load finishes.

DataContext — the public API pages actually use

DataContext.jsx wraps useUserData and exposes a flat object via useData():

  • Raw arrays: shifts, commutes, holidays, leaves, wfhLogs, leaveSettings
  • CRUD per entity: addShift/updateShift/deleteShift, addCommute/..., addHoliday/..., addLeave/..., addWfh/...
  • updateLeaveSettings(patch) — merges into the settings object
  • dedupeAll() — manual "Remove Duplicate Entries" button in Settings
  • replaceAll({...}) — used by JSON/Excel import (bulk overwrite)
  • clearAll() — wipes all data (Settings → "Clear All Data")

On every load, a useEffect in DataContext also runs de-duplication automatically (dedupeShifts, dedupeCommutes, dedupeLeaves, dedupeWfh from lib/) to clean up any legacy duplicate rows.

Typical "add an entry" flow (e.g. Shift Log)

User submits form in ShiftLog.jsx
→
addShift(entry)
→
DataContext: setShifts(prev => [...prev, entry])
→
useUserData's data state changes
→
setDoc() writes the whole doc to Firestore

There is no per-field Firestore write — any single change rewrites the entire document (merged). This is simple and fine at this data scale.

Theming ThemeContext.jsx

Dark/light mode is a device-local UI preference — stored in localStorage (key pt_theme), not synced via Firestore (it's not "tracker data"). Initial value falls back to the OS/browser's prefers-color-scheme.

useEffect(() => {
  document.documentElement.setAttribute('data-theme', theme);
  localStorage.setItem('pt_theme', theme);
}, [theme]);

All colors in index.css are CSS custom properties on :root, re-declared under :root[data-theme='light']. Flipping the data-theme attribute is the entire mechanism — no component re-render is needed for the color swap itself, only the toggle button's icon (Sun/Moon) reacts to theme state.

Per-section accent colors

Many cards/tables use a --card-accent variable (defaults to --accent) to tint their header/zebra-stripes/hover differently per feature area:

.card--green  { --card-accent: var(--accent-2); }   /* Expense Log */
.card--purple { --card-accent: var(--accent-purple); } /* Leave */
.card--teal   { --card-accent: var(--accent-teal); }   /* WFH */
.card--orange { --card-accent: var(--warn); }          /* Holidays */

th { background: color-mix(in srgb, var(--card-accent, var(--accent)) 14%, transparent); }

Requires a browser that supports CSS color-mix() (Chrome 111+/Firefox 113+/Safari 16.4+).

Sort & Filter System useSortFilter.js SortableTh.jsx

Every data table in the app (Shift Log, Expense Log, Leave/WFH, Holidays) uses the same two pieces:

useSortFilter(rows, getSearchText, sorters, initialSort)

  • getSearchText(row) — builds one lowercase string per row; the free-text box filters rows whose haystack includes the search term.
  • sorters — { columnKey: row => comparableValue }; clicking a column header toggles ascending/descending sort by that accessor.
  • Returns { search, setSearch, sortKey, sortDir, toggleSort, rows } — rows is the filtered + sorted output to render.

SortableTh

A <th> that calls onSort(sortKey) on click and shows ▲/▼ when it's the active column. Usage pattern repeated across pages:

const { search, setSearch, sortKey, sortDir, toggleSort, rows: sorted } =
  useSortFilter(shifts, searchTextFn, sorters, { key: 'date', dir: 'desc' });

<input className="table-filter" value={search} onChange={e => setSearch(e.target.value)} />
<SortableTh label="Date" sortKey="date" activeKey={sortKey} dir={sortDir} onSort={toggleTab} />

Feature: Shift Log Tab: Shift Log

Tracks daily punch-in/out and computes net worked hours.

Data shape

{ id, date, punchIn: "HH:MM", punchOut: "HH:MM"|null, breakMin, callMin, notes }

Core math — lib/shift.js

  • computeNetMinutes(shift) = (punchOut − punchIn) − breakMin + callMin (after-hours call time is added back, since it's extra work). Returns null if punch-out hasn't happened yet.
  • workdayBand(workdays) = { low: workdays × 7.2h, high: workdays × 8h } — the expected hour range for a week/period.
  • rangeWorkdayInfo(start, end, holidaySet, wfhSet) counts Mon–Fri days in a range, splitting them into real workdays vs. holidays vs. WFH days (both of the latter are excluded from the hour target — see box below).
  • weeklyStatus(totalHours, workdays) → badge class + label: Under / On Track / Over, compared against workdayBand.
Why WFH reduces the target: On a day logged as WFH, the user doesn't log a Shift Log entry (punch in/out), so that day shouldn't count toward the 36–40h/week office-attendance target — exactly like a holiday. This is why rangeWorkdayInfo takes both a holiday set and a WFH date set.

Feature: Expense Log Tab: Expense Log CommuteLog.jsx

Despite the file being named CommuteLog.jsx, this page now covers both daily commute trips and flat one-off expenses (Other Expense, My Amazon Expenses, Parents Expense).

Data shape

{
  id, date, type: 'commute' | 'other' | 'amazon-mine' | 'amazon-parents',
  period: 'morning'|'evening'|null,   // only for type:'commute'
  route, routeRemark, mode, modeRemark,   // only for type:'commute'
  payment, paymentRemark, fare, notes
}

Key concept — isOtherExpense(c)

In lib/commute.js, isOtherExpense(c) = c.type !== 'commute'. Anything that isn't a commute trip (Other/Amazon-mine/Amazon-parents) is a "flat expense" — not tied to a morning/evening period, and multiple can exist on the same date.

  • categoryText(c) → category label used everywhere (Auto/Metro for commutes, or the specific flat-expense label).
  • groupCommutesByDate(list) → one row per date: { date, morning, evening, other: [...] }, used by the "All Expense Entries" table (split further into 3 columns: Other Expense / My Amazon / Parents Expense by filtering other by type).
  • totalsByCategory(list) → { [categoryLabel]: totalFare }, feeds both the category table and the DonutChart.
  • ALL_CATEGORY_LABELS → fixed list of every possible category, so the breakdown table/chart always shows all categories (even ₹0 ones) instead of only ones with data.

Month navigation

The page keeps a monthAnchor date in local state; Prev/Next buttons call addMonthsFn(monthAnchor, ±1). All displayed data (monthCommutes, category totals, entries table) is filtered to c.date.slice(0,7) === monthKeyOf(monthAnchor) — so only one month's expenses are visible at a time, with a "Total Expenses" stat card for that month.

Feature: Leave & WFH Tab: Leave & WFH LeaveLog.jsx lib/leave.js

This is the most math-heavy feature — it models a real org leave policy and derives live balances purely from logged entries (there's no separate "balance" field persisted anywhere).

Policy constants (lib/leave.js)

TypeAccrualCarry-forward
Sick+1/month (credited on the 1st)No — resets every calendar year
Casual+1/monthNo
Annual+1.75/month (credited at month-end)Yes, capped at 45 total
Tenure+1/year if tenureEligibleNo
Wellness+1/monthNo — lapses at month end, can't bank it
WFHn/a — 26 days/year capn/a

How balances are computed — computeLeaveBalances(leaves, settings, asOf)

  • Sick/Casual/Tenure: accrued-so-far-this-year minus entries logged this year of that type. Simple, resets naturally every Jan 1 because the accrual formula is anchored to the current year.
  • Annual (carry-forward): anchored to a user-set annualOpeningBalance + annualOpeningDate (set once in Settings → Leave Policy, e.g. "42 as of 2025-12-31"). The function counts month-end accrual events strictly after that anchor date, subtracts annual leave logged after the anchor, and caps the result at 45 (ANNUAL_CARRY_FORWARD_CAP). Both the capped value (annual) and the true uncapped total (annualActual) are returned — the UI shows the actual number and only mentions the cap note once it's exceeded.
  • Wellness: 1 − (wellness entries logged this month), clamped to 0 — deliberately ignores all other months.

Warnings — monthlyWarnings(leaves, wfhLogs)

Returns an array of warning strings for the current month: WFH days > 2/month, or total leave days > 5/month. These render as orange banners at the top of both the Leave & WFH page and the Dashboard (reusing the same function, so the thresholds only live in one place).

Other helpers

  • wfhUsage(wfhLogs) → { usedThisYear, usedThisMonth, remaining } against the 26/year cap.
  • leaveUsageByType(leaves) → days availed per type this year, feeds the "Leave Days Availed by Category" table.
  • lastMonths(6) → rolling 6-month helper, kept for reuse elsewhere.
  • monthsOfYear(year) → all 12 months (Jan–Dec) of a calendar year; used to build the Leave Trend / WFH Trend ComboCharts so they show the whole current year rather than a rolling window.

Both the Leave entries table and the WFH entries table include a Day column (Mon–Sun) right after Date, computed via a small dayOfWeek(date) helper in LeaveLog.jsx (DOW_SHORT[(parseDateStr(date).getDay() + 6) % 7]) — the same pattern Settings uses for the Holidays table. It's wired into both useSortFilter calls so it's sortable and included in the free-text filter.

Dashboard Dashboard.jsx

A read-only aggregation view — it doesn't own any data, it just imports useData() and derives everything via useMemo:

  • stats — today's net hours, this week's hours + target status, this month's avg/week, week/month commute spend, month leave days, month WFH count. Also builds bannerText (over/under target warning, noting excluded holidays/WFH days) and reuses monthlyWarnings from leave.js.
  • hoursBars / expenseBars — last 6 weeks of data, rendered via ComboChart (bars + dashed average line).
  • breakdown — this month's expenses grouped by category, rendered via DonutChart.
  • recentShifts / recentCommuteGroups / recentLeaves / recentWfh — last 5 of each, shown in small tables at the bottom.

Each stat card has a colored StatIcon badge (icon + hex color passed as props) — these are independent of the CSS theme variables, so they stay vivid in both light and dark mode.

Reports Reports.jsx WeeklyReport.jsx MonthlyReport.jsx

Reports.jsx is just a sub-tab switcher (Weekly/Monthly) with its own subtabs nav; the real logic lives in the two child pages.

Important design decision: Trips vs. Other Expenses

Both report pages split commute data into two independent sections instead of one mixed "Commute Summary":

  • Trip Summary — only type === 'commute' entries (Auto/Metro rides). Shows total trip spend + a mode breakdown + the trip list.
  • Other Expenses Summary — everything else (isOtherExpense(c)). Shows total + category breakdown + entry list.

This exists because a flat "Trips" count used to incorrectly include Amazon/Other expense entries, which aren't trips at all.

Shift summary math

Reuses the exact same rangeWorkdayInfo / weeklyStatus / targetLabel functions from lib/shift.js as the Dashboard, so holidays and WFH days are excluded from the target band here too. MonthlyReport additionally buckets each week into its own row (grouping shifts/commutes/leaves/WFH by startOfWeek(date)).

CSV export

Every report section has an "Export … CSV" button calling downloadCsv(rows, COLUMNS, filename) from lib/csv.js — COLUMNS is a declarative list of { key, label } (key can be a field name or a function for computed columns, e.g. Net Hours). Rows are automatically sorted most-recent-first before writing.

Settings Settings.jsx

Four independent cards:

  1. Company Holidays — simple add/remove list; holidays feed into the Shift target-band calculations app-wide.
  2. Leave Policy — tenureEligible checkbox + annualOpeningBalance/annualOpeningDate inputs, written via updateLeaveSettings(). This is the "anchor" described in the Leave & WFH section above.
  3. Backup & Restore — exportJson() dumps the whole data shape (shifts/commutes/holidays/leaves/wfhLogs/leaveSettings) to a downloadable .json file; importJson(file) reads it back and calls replaceAll() after a confirm dialog.
  4. Excel Sync — exportExcel()/importExcel() (lib/excel.js) do the same round-trip but as an .xlsx workbook with one sheet per entity (Shifts/Commutes/Holidays/Leaves/WFH) — handy for manually syncing between two devices via OneDrive/Drive. Rows are sorted most-recent-first, columns are auto-sized to fit their longest value (capped at 40 chars so one long note can't dominate the sheet), and the id column is omitted from the export (optional on import — missing IDs just get freshly generated).

Both backup paths are type-agnostic for the Expense Log's type field — the Excel importer preserves whatever string is in the type column instead of assuming only 'commute'/'other', so new expense categories round-trip correctly.

Firebase Setup

Configured once in the Firebase Console (not in this repo, since it's account/project-level config):

  • Authentication → Sign-in method: Google provider enabled.
  • Authentication → Authorized domains: must include localhost (usually default) and <username>.github.io (the GitHub Pages domain), otherwise sign-in fails with auth/unauthorized-domain once deployed.
  • Firestore → Rules: restricts every user to their own document:
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}

Adding new fields to the stored document (as this app has done repeatedly — leaves, wfhLogs, leaveSettings, new expense types) never requires a Firebase Console change, since Firestore is schemaless and the rule above already covers the whole per-user document.

Conventions & Tips for New Contributors

  • Business logic lives in lib/, not in components. Pages call pure functions from lib/ and mostly just handle form state + rendering. When fixing a calculation, look in lib/ first.
  • Every list page follows the same shape: an "Add/Edit Entry" form card at the top, then a filterable/sortable table card below, built with useSortFilter + SortableTh.
  • Duplicate-prevention pattern: before addX(entry), check list.some(x => x.date === entry.date && ... && x.id !== entry.id) and show a toast instead of saving. Applied consistently to shifts (per date), commutes (per date+period), leaves (per date+type), and WFH (per date).
  • Color system: don't hardcode colors in CSS — use the --accent/--accent-2/--accent-purple/--accent-teal/--warn/--bad variables so the light/dark theme toggle keeps working. StatIcon and category-dot colors are the one place fixed hex values are intentionally used (so icon badges stay vivid regardless of theme).
  • Adding a new persisted field: update the EMPTY/default object in useUserData.js, add it to DataContext's destructure + CRUD methods + replaceAll/clearAll, and (if it should survive backup/restore) wire it into exportJson/importJson in Settings and exportExcel/importExcel in lib/excel.js. No Firebase Console changes are ever needed for this.
  • Adding a new tab: create the page component, add it to PAGES in App.jsx, and add a matching entry (key/label/icon/color) to TABS in Header.jsx.
